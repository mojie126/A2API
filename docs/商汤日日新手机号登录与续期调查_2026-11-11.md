# 商汤日日新手机号登录与续期调查_2026-11-11

## 结论摘要

商汤日日新控制台当前只保留手机号验证码登录，账号密码登录已不可用。手机号验证码登录复用控制台原有 OAuth 授权码 + PKCE 流程，授权码换票会同时下发 access token 与 refresh token。

2026-11-12 已在真实账号上完成实测：授权码换票返回非空 refresh token，连续两次 `grant_type=refresh_token` 刷新均为 HTTP 200，且两次刷新后 refresh token 都发生变化，说明当前账号支持 refresh token 轮换与自动续期。本次已据此改完添加账号、账号设置与余额查询链路，不再依赖控制台账号密码。

## 已核实的上游链路

控制台登录页的公开前端资源显示：

1. 页面进入时先请求 `GET https://iam.sensecoreapi.cn/iam/authn/v1/auth/checkChallenge?challenge=<login_challenge>`，确认登录挑战有效。
2. 手机号发码调用 `POST https://iam.sensecoreapi.cn/iam/authn/v1/auth/nova/sendSmsCode`，请求字段为 `phone`、`region_code`，可能附带图形验证的 `code_key`。
3. 手机号验证码校验调用 `POST https://iam.sensecoreapi.cn/iam/authn/v1/auth/nova/smsLogin`，请求字段为 `token_code`、`verify_code`、`challenge`。
4. 校验成功后，响应里的 `redirect`、`redirect_uri` 或 `redirect_to` 会跳回 OAuth 流程；单租户直接跳转，多租户先选择租户，再由 `loginNext` 完成跳转。
5. 最终统一进入 `https://platform.sensenova.cn/oauth2/token` 的授权码换票流程，使用 `authorization_code`、`client_id=nova`、`code_verifier`、`redirect_uri`、`state` 换取 `access_token`、`id_token` 与 `refresh_token`。
6. 控制台客户端在收到 401 时会使用 `grant_type=refresh_token` 调用同一令牌端点，成功后更新 access token 与 refresh token，再重放原请求。

因此，“手机号验证码登录”和“账号密码登录”不是两套独立的续期机制，它们共用最后的 OAuth 授权与 refresh token 续期机制。

## 现有网关实现

商汤日日新是自定义提供商，余额查询方案为 `sensenova`。旧实现只支持控制台账号密码登录，当前已改为：

1. 发起 OAuth 授权并跟随跳转，取得 `login_challenge`。
2. 调用 `nova/sendSmsCode` 发送短信验证码，网关侧暂存 `token_code`、PKCE verifier、state 与 Cookie。
3. 用户填入验证码后调用 `nova/smsLogin`；多租户时再调用 `nova/loginNext`。
4. 跟随登录返回的 redirect，取得一次性授权码。
5. 用授权码换 access token 与 refresh token，按账号加密保存。
6. access token 临期时使用 refresh token 续期；上游轮换后的 refresh token 原子回写账号记录。

旧记录里仍可能残留 `username` / `password`，登录成功后由后端清除；公开接口只返回脱敏手机号、`hasRefreshToken` 等标记，不返回 access token 与 refresh token。

旧实现现场查询 `custom-acct-c1efba5d3864` 时曾返回：

```text
商汤账号登录失败：PermissionDenied
```

该问题是上游关闭账密登录导致的历史现象；新实现改走手机号验证码后不再使用这条登录路径。

## 已落地的适配方案

手机号授权已确认能返回可用 refresh token，现按以下方式接入：

| 层次 | 方案 |
|---|---|
| 添加账号 | 商汤预置卡与已有提供商都显示手机号验证码登录：手机号、发送验证码、输入验证码、完成登录 |
| 首次登录 | 由网关发起 OAuth 授权，取得 `login_challenge`，调用 `nova/sendSmsCode` 与 `nova/smsLogin`，继续授权码回调并换取 token |
| 凭证保存 | 保存 access token、refresh token、手机号与到期时刻；按账号记录整行加密，不在公开账号形态中返回令牌本体 |
| 自动续期 | access token 临期时使用 refresh token 调用 `oauth2/token`；refresh token 每次轮换后原子回写 |
| 失败处理 | refresh token 失效时明确提示重新发送验证码，不再回退已失效的控制台账密登录 |
| 余额查询 | 使用续期后的控制台 access token 查询 `platform.sensenova.cn/lite/console/v1/tokenplan/pool-usage`，按通用池与 Flash-Lite 专属池拆分展示 |
| 账号页展示 | 复用果办、Trae 的下拉式余额明细：账号行显示最低剩余比例或总额，展开后显示 5 小时、7 天、活动返赠和到期时间 |
| 添加账号表单 | 商汤余额查询段只显示手机号验证码登录，控制台账号密码字段已移除；API Key 仍用于推理转发 |

安全边界：

1. 验证码只在本次登录会话内使用，不落盘。
2. refresh token 与 access token 按账号记录整行加密保存，公开接口只返回 `hasRefreshToken` 等标记。
3. 同一账号的 refresh 必须串行化，避免一次性 refresh token 被并发消费。
4. 登录和刷新失败不得把旧 token 当新结果返回。
5. 不绕过图形验证、滑块或短信验证码。

## 实测记录

2026-11-12 使用手机号验证码登录后的真实授权结果：

| 检查项 | 结果 |
|---|---|
| 授权码换票 | HTTP 200，access token 与 refresh token 均非空 |
| access token 有效期字段 | `expires_in` 约 3 小时 |
| 第 1 次 refresh | HTTP 200，refresh token 发生轮换 |
| 第 2 次 refresh | HTTP 200，refresh token 再次发生轮换 |
| 刷新后的 access token | 有效，长度与首次一致 |
| 直连发码 | HTTP 200，`token_code` 为空，返回“先过人机验证”的信号 |
| 官方滑块资源 | `getCaptcha` 返回 `code_key`、背景图与拼图块 |

验证过程只记录 HTTP 状态、字段是否存在、长度与 JWT 到期时刻，未把令牌本体写入文档、日志或对话。

## 实施落点

| 层次 | 落点 |
|---|---|
| 授权链路 | `core/providers/custom/sensenova_auth.rs`：发码、短信登录、租户选择、授权码换票、refresh token 续期 |
| 网关接口 | `POST /api/sensenova/sms/send`、`POST /api/sensenova/sms/verify` |
| 人机验证 | `POST /api/sensenova/sms/captcha`：展示官网返回的背景图与拼图块，用户拖动后调用 `checkCaptcha`，通过后重新发码 |
| 账号存储 | `custom_accounts::store_custom_balance_sensenova_login` 加密保存手机号、access token、refresh token 与到期时刻 |
| 余额查询 | `custom/balance.rs` 优先用 refresh token 续期，再调用双积分池用量接口 |
| 添加账号 | 商汤预置卡与已有提供商表单改为手机号验证码登录 |
| 账号设置 | 「查询设置 → 查询凭证」改为手机号验证码重新登录，成功后刷新账号读数 |

验证码不进入前端持久草稿；网关侧 pending ticket 十分钟过期，验证成功后立即删除；网关重启使未完成的登录失效，用户重新发码即可。

上游直连发码会返回 HTTP 200 但 `token_code` 为空，官网用这个信号要求先完成滑块。网关已按同一协议接入 `getCaptcha` / `checkCaptcha`，前端显示官方图片与拖动条，只接收用户完成后的偏移值，不自动破解或代替用户操作人机验证。

## 果办模型目录 401 调查

模型目录失败账号为：

```text
officeace-a6c870e3f045
```

手动刷新返回：

```text
OfficeAce 模型目录返回 HTTP 401（网关不接受这条凭据？）
```

使用同一账号执行真实模型测试返回：

```text
上游返回 401: {"error_code":"APIG.1009","error_msg":"AppKey or AppSecret is invalid"}
```

控制面套餐查询仍正常返回 `active`，说明控制面临时 AK/SK 与订阅状态正常。失败的是模型网关 Basic 凭据，即账号记录中的 `modelAppKey` / `modelAppSecret`。目录刷新与对话转发使用同一对凭据，因此目录 401 不是独立的目录接口故障。

处理建议：

1. 在果办网页登录流程重新授权，获取新的模型网关 Basic 凭据，再刷新模型目录。
2. 不要通过控制面 refresh token 刷新模型网关 Basic 凭据；现有续期链只更新临时 AK/SK、STS 与 project_id。
3. 重新授权后执行一次模型目录刷新与一次最小模型测试，两者都成功才能视为恢复。
4. 若重新授权后仍返回 `APIG.1009`，检查官方账号是否被吊销模型网关权限或模型网关地址是否变化。
