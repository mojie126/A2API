# A2API 官方 beta 跟进清单（2026-11-19）

本文给出网关仓库（A2API）相对官方 beta 分支的跟进现状与待办分类。判定依据：本地 `develop` 与 `upstream/beta` 的文件比对、本地模块清点、官方提交说明。执行顺序按「投入产出」排列，不按官方提交顺序。

## 一、当前基线

| 项目 | 本地 develop | 官方 beta | 差距 |
| --- | --- | --- | --- |
| 版本号 | `3.5.0-beta.1` | `3.5.0-beta.3` | 差两个 beta |
| 官方基线提交 | `aba58858`（beta.1） | `cd0411bf`（beta.3） | 缺 `0affd3af`（beta.2，1175 个文件）与其后 9 个提交 |

## 三、建议跟进（主面板侧功能，投入较大）

### 3.1 官网更新通道（优先级最高）

官方 beta.2 把软件与插件的更新检查整体改到官网站点 `https://agent2api.dev`，删除 GitHub 线路的探测、限流、源选择与令牌缓存。

- 新增 `core/update/website.rs`（145 行）：`ORIGIN` / `API_BASE` / `PLUGIN_BASE` 常量与 URL 白名单校验
- 删除 `core/update/` 下 `probe.rs`、`rate_limit.rs`、`selection.rs`、`source.rs`、`source_state.rs`、`token.rs`
- 改动 `check.rs`（+34/-103）、`index.rs`、`download.rs`、`integrity.rs`、`client.rs`、`selfupdate.rs`
- 前端：`ui-islands/src/islands/update-settings.tsx`、`mobile/src/components/AppUpdatePanel.tsx`、新增 `mobile/src/components/UpdateProxySettings.tsx`

**决策点**：本地 fork 的更新源是自建 GitHub Releases（`fork-build.yml` 产出草稿），官方官网只托管官方安装包，跟随后本地更新将指向官方站点，fork 的专属构建会失去更新通道。是否跟进需先定 fork 的更新策略；若不跟进，至少要吸收 `website.rs` 的 URL 白名单校验思路用于现有 GitHub 线路。

### 3.2 统一错误处理设置

按限流、额度耗尽、登录失效、连接异常分别配置重发、换号、冷却与失败保护。

- `config/error_policy.rs`（132 行）、`config/error_policy_types.rs`（155 行）、`api/routing-errors.tsx` 配套面板
- 本地 `core/upstream/` 已有轮换与冷却逻辑，需判断是替换还是并存

### 3.3 运行容量管理

自动或手动设置对话、登录、后台任务、图片任务的并发与排队上限。

- `config/runtime_capacity.rs`（129 行）、`api/runtime_capacity.rs`（31 行）、`api/capacity_admission.rs`（58 行）、`core/runtime_capacity/`（5 个文件）
- 本地已有 `core/limiter` 与 `routing_concurrency.rs`，属同类但口径不同，需先对齐语义再合并

### 3.4 系统提示词规则

按提供商、客户端、模型匹配，选择替换、追加或透传，可预览命中结果。

- `config/prompt_rules.rs`（115 行）、`api/prompt_rules.rs`（136 行）、`ui-shared/settings-prompt-*.tsx`（约 8 个文件）
- 本地 `core/prompt.rs` 已有系统提示词三模式（透传/替换/追加）的全局版本，官方是规则化的升级版

### 3.5 订阅接入（Claude / ChatGPT / Codex）

- `core/providers/chatgpt_subscription/`（13 个文件）、`core/providers/claude_subscription/`（15 个文件）
- 官方自述「相关链路尚未完成真实账号验收」，本地无账号无法验证；建议延后

### 3.6 账号列表分页与实时状态

- `api/accounts_list.rs`（55 行）、`api/accounts_credentials.rs`（52 行）、`api/accounts_usage_snapshot.rs`（54 行）、`core/accounts_list/`（2 个文件）

### 3.7 插件相关增强

- 插件批量安装、更新、启用、停用、卸载：`core/plugin_host/packages/`（6 个文件）+ `provenance.rs`

## 四、不跟进（架构决策）

| 官方内容 | 规模 | 不跟进理由 |
| --- | --- | --- |
| `core/plugin_host/wasm/` 扩展 | 234 个新文件（本地 16 个） | 官方把全部提供商转独立 WASM 插件，宿主为此扩展了 `managed_task`、`catpaw_turn`、`desktop_credentials`、`checkin_call` 等专用通道；本地保持原生插件 + script（Bun）体系，装官方 WASM 插件的场景有限，宿主能力按需再说 |
| `wasm/` 目录下的 38 个提供商 | — | 与插件仓库同一决策：不迁 WASM 架构 |
| `core/plugin_host/script/website.rs` | — | 官网插件源的配套，随官网更新通道决策 |
| 官方 `crates/providers` 降级 | — | 官方 beta.2 起原生实现不再构建发布，本地仍以原生为主 |

## 五、执行建议

1. **先做第二节 8 项**：改动小、风险低、与架构无关，可一次合并完成
2. **再定官网更新通道**：这是唯一需要先做产品决策的项（fork 的自建构建要不要保留更新能力）
3. **最后按需挑第三节**：错误处理、运行容量、提示词规则三者都触及请求管线与配置层，建议一次性设计，避免反复改 `config/mutations.rs` 与 `api/mod.rs`
4. 合并前先把本地 `SCHEMA_VERSION` 32 与上游 30 的编号差对齐（本地新增列要保留，官方新增表要重编号到 33 起）
5. 协议库依赖 tag 与工作流校验同步调整：协议库最高只有 `v3.5.0-beta.2`
