# ZCode 免费套餐并发限制与 WARP 出口池方案（2026-11-17）

## 一、结论

ZCode 免费套餐（套餐池通道）的并发 429 不是单账号额度耗尽，而是上游按用户与出口维度判定的并发限制。实测结果表明：

- 同一出口 IP 下，一个请求在途时，另一个请求即使换用其他 zcode 账号仍返回 429
- 换到不同出口 IP 后，两个请求可以同时成功

因此可以参考 opencode2api 的出口池做法：为 ZCode 请求准备多个出口，429 时切换出口重发，对客户端保持无感。

## 二、实测记录（2026-11-17）

### 2.1 上游原始响应

```text
POST https://zcode.z.ai/api/v1/zcode-plan/anthropic/v1/messages
HTTP 429

{"code":3008,"msg":"user concurrency limit exceeded","logid":"..."}
```

响应头没有 `Retry-After`，也没有 `x-ratelimit-*` 字段。

### 2.2 对照实验

| 场景 | 结果 |
| --- | --- |
| A（家宽出口）在途，B 使用同一出口的另一个 zcode 账号 | B 返回 429，`upstream_code=3008` |
| A（家宽出口）在途，B 使用新加坡出口 | B 返回 200，1.35 秒完成 |
| 两者都使用家宽出口，临时 Key 仅允许 zcode / zcode-intl | 依次尝试多个账号全部 429，最终返回网关合成的 429 |

### 2.3 网关当前行为

- `Agent2Providers` 的 `zcode/errors.rs` 把 429 与业务码 1005 归类为 `QuotaLimited`
- 网关收到 `QuotaLimited` 后标记该账号对该模型冷却，再顺延下一个账号
- 换账号不能绕开该限制，结果是所有候选账号被依次标记冷却，最终整条请求链返回 429

## 三、opencode2api 的做法

opencode2api 是 OpenCode Zen / Zen Go 的网关，核心机制：

- 支持手动 HTTP / HTTPS / SOCKS5 代理池与用户态 Cloudflare WARP 出口池
- 免费模型请求按在途请求分配出口，出口第一次收到 429 或 403 即淘汰并换下一个
- IPv6 出口按 `/64` 去重并冷却 30 分钟，IPv4 出口按 `/32`
- 代码注释明确说明 OpenCode Zen 的免费层按 IP 限流，换代理就是故障转移手段
- README 说明上游免费额度按出口网段计算，只有换到不同网段才有意义

其可借鉴的部分是“出口池 + 按连接或请求分配出口 + 429 淘汰出口”，不要求 ZCode 使用同一套 WARP 实现。

## 四、目标

1. 客户端无感：调用方仍然只配置一个模型名与一个 Key，不感知出口切换
2. ZCode 账号配置一次轮询档后，网关自动在多个出口之间分配请求
3. 遇到 `3008` 时先原地换出口重发，不立即把账号标记为额度冷却
4. 所有出口都 429 时保留现有兜底：按账号限额冷却并顺延下一个账号

## 五、总体架构

```text
客户端
  └─ A2API 网关
       ├─ 账号轮询档（source=rotate）
       │    └─ 代理池：多个 WARP SOCKS5 出口
       ├─ 429 换出口重试（同一账号，换下一个出口）
       └─ WARP 出口池 sidecar（用户态，多出口）
            └─ 每个出口一个 SOCKS5 端口，或单端口按连接轮换
```

职责划分：

- WARP sidecar 只负责提供多个可用出口，不参与账号与模型路由
- A2API 负责出口池选择、429 重试、请求日志与冷却兜底
- 账号配置只声明“使用轮询档”，不感知具体出口数量

## 六、实施步骤

### 6.1 网关侧：内置提供商支持 429 换出口

现状：`attempt_custom` 已实现轮询档 429 换出口，但 ZCode 是内置插件，走 `attempt_queue` 的无状态路径，没有这段补救。

落点：

- 文件：`desktop-tauri/src-tauri/server/src/server/core/upstream/provider_loop.rs`
- 函数：`attempt_queue`
- 复用：
  - `core::proxy_rotate::next` 或 `AccountStore::next_rotate_proxy`
  - `provider_loop::MAX_ROTATE_EXIT_RETRIES`
  - `telemetry.note_attempt_retry`

逻辑：

1. 发送前判断当前账号是否为轮询档（代理配置 `source=rotate`）
2. `send_with_retry` 返回 `QuotaLimited { status: 429 }` 时：
   - 若为轮询档且剩余换出口次数大于 0，取下一个出口
   - 更新本轮 `proxy`，重建 `TransportRequest`
   - 在同一账号上原地重发，不标记账号冷却，不消耗换号预算
   - 记录一次内部重试，请求日志显示“轮询换出口”
3. 换满 `MAX_ROTATE_EXIT_RETRIES` 仍为 429 时，交回原有逻辑：标记账号冷却并顺延
4. 非轮询档账号与非 429 错误保持现状，避免影响其他提供商

验收：

- 轮询档 + 429：请求日志出现“轮询换出口”明细，最终成功或按原逻辑失败
- 静态代理、直连、非 zcode 提供商：行为与改动前一致

### 6.2 进程内 WARP 出口池

实际实现不是独立 sidecar，而是网关进程内的用户态出口池（`core/warp`）：

- `register`：注册 / 注销 WARP 设备
- `tunnel`：`boringtun` WireGuard 握手与加解密，UDP 承载
- `netstack`：`smoltcp` 用户态 TCP/IP，DNS 与 TCP 连接
- `socks`：每个出口一个本地 SOCKS5 回环端口
- `pool`：出口轮询、首个出口就绪即发布、其余出口后台补齐

设备只在**本次服务运行期间**复用，不写磁盘。WARP 设备与私钥绑定当前环境，跨平台或跨设备搬移没有意义，也不应进入 WebDAV 备份与同步；服务重启后重新注册。
- 出口代理必须按普通本地 SOCKS5 使用（`nonDirect=false`）：标成非直连会被代理链判定为「需要系统代理中转」，在没有系统代理的容器里会直接失败

资源开销与并发：

- 每个出口约几 MB 内存（WireGuard 状态 + smoltcp 接口 + 每连接约 64 KiB 收发缓冲），CPU 只在有流量时消耗
- 默认 2 个出口：兼顾启动速度与并发；设备注册是串行 HTTP 调用并有 Cloudflare 限流，出口越多首次启动越慢
- 出口数量由 `ZCODE_WARP_POOL_SIZE` 控制，范围 1–32，默认 2
- 账号数量不等于出口数量：出口数按期望并发设置；同一出口可以承载多个请求，但上游按出口 IP 的限制仍会生效

IPv6：

- 默认先使用 IPv4 端点（本环境实测 WARP IPv6 端点不可达）
- 家宽具备可直接访问 WARP IPv6 端点的网络时，可设 `ZCODE_WARP_IPV6=1` 优先尝试 IPv6 端点
- 多个 WARP 设备的 IPv4 出口共享 NAT，出口 IP 可能相同；需要不同出口 IP 时依赖 IPv6 `/64` 或后续 `source_ipv6` 绑定

### 6.3 账号开关与自动使用

1. ZCode / zcode-intl 账号新增 `zcodeEgressPool` 开关，默认开启
2. 开启时网关自动把该账号的请求代理指向当前出口池，用户不需要在「网络代理」页配置任何 WARP 条目
3. 关闭或出口池未就绪时，回退账号原代理或直连
4. 429 时：池内有多个出口则轮换到下一个；只有一个出口时注册一台新设备追加到池中再试，不把账号标记为额度冷却

### 6.4 可观测性

- 请求日志：本轮尝试明细里追加“轮询换出口重试”，不新增 attempt
- 运行日志：只记录出口池状态变化与出口端口 / IP，不按请求刷屏
- 请求日志客户端列：新增 WARP / 代理标签（非直连才显示），悬停显示出口 IP
- 出口池没有独立 sidecar 健康检查，状态通过 `[WARP]` 日志与请求日志观察

## 七、部署与运行

出口池内置在网关进程，不需要额外容器或代理条目。

- 运行要求：宿主机或容器能向 Cloudflare WARP 端点发送 UDP（常用端口 2408）
- Docker：无需额外挂载或权限；镜像内的网关直接注册设备
- Windows：已在本机构建并启动验证，成功注册 2 个出口、请求日志记录 `warp` 出口
- 出口数量：`ZCODE_WARP_POOL_SIZE=1..32`，默认 2
- 出口设备：只在本次运行期间复用，服务重启后重新注册；不写磁盘，不进入 WebDAV 备份与同步
- 容错：池初始化失败按指数退避重试；单个出口隧道失败时注销并重新注册；429 时优先轮换出口，出口不足时追加新设备

## 八、验证步骤

1. 基线复现：同一出口下，长请求在途时发短请求，确认返回 429 与 `upstream_code=3008`
2. 换出口验证：长请求走出口 A，短请求走出口 B，确认两个请求都成功
3. 出口池验证：
   - ZCode 账号保持默认开启出口池
   - 长请求在途时发短请求
   - 确认短请求先 429、随后换出口或追加新设备后重试成功
   - 确认账号没有被标记为额度冷却
4. 兜底验证：关闭出口池或让所有出口不可用，确认请求回退账号原代理或直连
5. 回归验证：关闭开关的 ZCode 账号、非 zcode 提供商的转发行为与改动前一致

## 九、风险与回滚

风险：

- WARP 出口可能被上游风控或共享出口网段影响，仍出现 429
- WARP 设备注册存在限流，池子不能无限扩大
- IPv4 出口通常是共享 NAT，优先使用 IPv6 出口
- 上游可能调整并发判定策略，方案需要随上游行为复核

回滚：

- 账号页关闭「使用 WARP 出口池」，立即回退账号原代理或直连
- 出口池随网关进程启动与停止，无独立进程
- 网关侧换出口逻辑只对开启开关的 ZCode 账号生效

## 十、验收标准

- 同一出口并发时返回 429 的现象可稳定复现
- 不同出口并发时两个请求均成功
- 轮询档下 429 自动换出口，客户端只看到一次成功响应
- 请求日志能看出“换出口”这一内部动作
- 非轮询档路径无行为变化，现有测试全部通过

### 12.1 IPv6 出口实测（2026-11-17 复核）

- IPv4 出口共享已复核：同一进程内两台设备（以及此前三台）的出口 IPv4 均为 `104.28.225.103`
- 隧道内 IPv6 出网可用：经出口本地 SOCKS5 请求 `https://[2606:4700:4700::1111]/cdn-cgi/trace` 返回 200 与 `warp=on`，两台设备出口 IPv6 分别为 `2a09:bac5:1eed:3141::4e8:77` 与 `2a09:bac5:1eeb:1846::26b:4f`，同一设备重复请求稳定、两台设备不同，说明每台设备有独立 IPv6 出口，且不依赖本机 IPv6 路由（外层仍走 IPv4 端点）
- 但 ZCode 上游无法使用该出口：`zcode.z.ai` 经 CNAME `zcode.z.ai.a1.initaa.com` 只解析出 IPv4（`124.160.144.209` 等），`zcode-intl.z.ai` 同样没有 AAAA；请求目标是 IPv4-only，只能走 WARP IPv4 共享出口
- 代码现状与之相符：`netstack` 只对目标做 A 查询（`DnsQueryType::A`），字面 IP 直接透传；因此双栈域名一律走 IPv4，IPv6 出口目前只在客户端直接给出 IPv6 地址时可用
- 结论：多设备 IPv6 出口可用于访问双栈或 IPv6-only 上游，但对 ZCode 并发限制没有帮助；另行区分 ZCode 出口需要非 WARP 的多 IPv4 代理池

### 12.2 账号代理引用 WARP 设备（2026-11-18）

- 账号代理新增 `source=warp` 引用，只保存设备 id；本地 SOCKS5 端口与出口 IP 在解析时从出口池读取，设备重建后无需改账号配置
- 账号代理表单与账号页代理列提供「WARP 设备」选择，选项展示设备名与出口 IP，选中即保存；设备已删除或重启重建时提示重新选择
- 代理列按代理配置、代理池与设备清单版本重绘，后台自动刷新不重建下拉；余额查询的出网指纹同步纳入设备
- 更新出网与模型目录刷新共用同一条出口解析，`/api/update/proxy` 也可保存 WARP 设备引用；自动维护页「模型目录更新」的代理列与账号页代理列使用同一套缓存与选项构造

### 12.3 直连优先判定修复（2026-11-22）

- 缺陷：容量准入 `account_admission::select` 在返回前已把当前请求预占进连接计数，`zcode_direct_in_flight` 未排除自身，每个首次 ZCode 请求都被判成「直连已被占用」而无条件切 WARP
- 修复：`Connections::any_in_flight` 回调增加在途数，判定排除「当前账号且在途数 ≤ 1」，并补 `warp_enabled_for` 外层门控
- 口径确认：第二个请求改走 WARP 只针对 ZCode 国内 / 国际版，其他提供商即使命中并发或 429 也不进入该分支
- 验证：`cargo check --release -p agent2api-server` 与 `cargo test --release -p agent2api-server zcode_direct` 4 项通过
